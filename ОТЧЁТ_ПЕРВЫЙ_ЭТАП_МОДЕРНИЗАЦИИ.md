#### 3.1 Таблица блокировок в D1
- ✅ **Создано автоматически:** `CREATE TABLE IF NOT EXISTS user_blocks`
- **Структура:**
  ```sql
  blocker_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE
  blocked_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE
  created_at INTEGER NOT NULL
  PRIMARY KEY (blocker_id, blocked_id)
  ```

## ⚠️ ИЗВЕСТНЫЕ ОСОБЕННОСТИ И РЕКОМЕНДАЦИИ

### 1. **Фильтрация на клиенте**
- Блокировка проверяется **только на фронтенде** при отправке сообщения
- **Рекомендация (для будущих версий):** Добавить серверную валидацию в `handleSaveChatMessage()` в worker.js для дополнительной безопасности

### 2. **Хранение истории заблокированных сообщений**
- Сообщения от заблокированных пользователей **скрыты от отправителя**, но **остаются в БД**
- Это нормально: при разблокировке пользователь может увидеть сообщения, отправленные во время блокировки
- **Альтернатива (не реализована):** Удалять сообщения при блокировке (более агрессивно)

### 3. **Асимметричная блокировка**
- Текущая реализация: **A блокирует B** = **A не видит B, B не может писать A**
- **Это корректно:** Блокировка должна быть одностороннней (только блокирующий решает)
- **Если нужна взаимная блокировка:** Потребуется изменение логики в `isUserBlocked()` на обе проверки

### 4. **Проверка блокировки перед отправкой**
- Добавлена проверка: "Вы не можете отправить сообщение ID XXX, потому что вы блокировали этого пользователя или он заблокировал вас."
- **Нюанс:** Формулировка может быть уточнена — она не различает две ситуации (кто именно заблокировал)
